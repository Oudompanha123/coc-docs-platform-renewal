# Use Case UC-006: Upload and insert an image

> **REQ-ID**: UC-006
> **Version**: 1.0
> **Preceding Document**: [REQUIREMENTS-SPEC.md](../REQUIREMENTS-SPEC.md)

> **Entirely new capability.** The current site contains **zero images** — every visual is hand-authored inline SVG — and there is no upload, storage, or asset-handling pattern anywhere in the codebase. Nothing here extends an existing feature.

---

## 1. Scenario Overview

| Item | Description |
|------|------|
| **Primary User** | `admin` (non-technical) |
| **Preconditions** | Signed in as `admin`; a page is open in the editor |
| **Trigger** | The explanation needs a screenshot |
| **Outcome (Success)** | The image is stored, inserted in the page, and visible to readers |
| **Outcome (Failure)** | Upload rejected with a plain-language reason and logged; nothing partially stored |
| **Related FR** | FR-MEDIA-001, 002, 003, 004, 005 · FR-OPS-003 |
| **Related NFR** | NFR-SEC-UPLOAD, NFR-USE-01, NFR-USE-02, NFR-COMPAT-01 |
| **Related BR** | BR-022, BR-028, BR-030 |

> **Why this is in MVP**: the first instinct of a non-technical person in a WYSIWYG is to paste a screenshot. Without it they are blocked on day one and return to the PM — defeating the project's stated purpose.

## 2. Main Flow

| Step | Actor | Action | System Response |
|------|------|------|------------|
| 1 | `admin` | In the editor, adds an image block to the page body (**FR-MEDIA-002**) | File picker or drag-and-drop target appears |
| 2 | `admin` | Selects or pastes an image | Client-side size and type pre-check |
| 3 | System | — | Server validates **declared type, actual content type, and size** (**FR-MEDIA-004, NFR-SEC-UPLOAD**) |
| 4 | System | — | Stored **outside any executable path**; a stable reference is returned |
| 5 | `admin` | Enters alternative text | Alt text stored with the block (**FR-MEDIA-005**) |
| 6 | `admin` | Publishes the page | Image renders for readers at the page minimum role |

## 3. Alternative Flow

### 3.1 A-1: Reuse an existing image (**FR-MEDIA-003**)
- Action: the admin browses the media library and picks an existing item
- Outcome: inserted by reference; no duplicate upload

### 3.2 A-2: Delete an unused image
- Action: the admin deletes a media item
- Outcome: deletion refused, or clearly warned, if any page still references it

### 3.3 A-3: Paste directly from the clipboard
- Action: the admin pastes a screenshot straight into the editor
- Outcome: treated exactly as an upload, with the same validation. **This is the path a non-technical user is most likely to take, so it must not be an afterthought**

## 4. Exception Flow

### 4.1 E-1: Disallowed file type (**FR-MEDIA-004**)
- Action: rejected before storage; reason stated plainly; logged (**FR-OPS-003**)
- Outcome: an executable or script file cannot be stored, whatever its extension claims

### 4.2 E-2: Content type does not match the extension
- Action: rejected on actual sniffed content, not the filename
- Outcome: **content-type confusion attacks blocked.** Checking the extension alone is not sufficient

### 4.3 E-3: Oversized file
- Action: rejected with the limit stated; logged

### 4.4 E-4: Storage unavailable
- Action: upload fails cleanly; the page draft and its other blocks are preserved
- Outcome: no orphaned reference to an image that was never stored

### 4.5 E-5: Storage quota exceeded
- Action: upload refused; `super admin` alerted
- Outcome: bounded growth; no silent failure

## 5. Non-Functional Requirements Mapping

| NFR-ID | Application |
|--------|------|
| **NFR-SEC-UPLOAD** | Steps 3–4. New attack surface (RISK-006): declared type, sniffed content type, size, and storage location outside executable paths |
| NFR-USE-01 | Insert-a-screenshot is part of the unassisted task test — it is what a real editor will try first |
| NFR-USE-02 | No knowledge of file paths, storage, or CDN configuration required |
| NFR-COMPAT-01 | Images render correctly on mobile viewports |
| NFR-OPS-BACKUP | Uploaded media is inside the backup scope (BR-028) |
