# Use Case UC-003: Reorder and rename navigation

> **REQ-ID**: UC-003
> **Version**: 1.0
> **Preceding Document**: [REQUIREMENTS-SPEC.md](../REQUIREMENTS-SPEC.md)

---

## 1. Scenario Overview

| Item | Description |
|------|------|
| **Primary User** | `admin` (non-technical) |
| **Preconditions** | Signed in as `admin`; the section has at least two pages |
| **Trigger** | The reading order no longer matches how people actually learn the material |
| **Outcome (Success)** | Reader navigation reflects the new order and labels immediately |
| **Outcome (Failure)** | Previous order intact; nothing partially applied |
| **Related FR** | FR-NAV-001, 002, 003, 004, 005, 006 |
| **Related NFR** | NFR-USE-02, NFR-PERF-02 |
| **Related BR** | BR-002, BR-003 |

> **What this replaces**: today, order lives as array-literal order duplicated in **three hand-synchronised places** — `lib/i18n.ts` slug arrays, `Sidebar.tsx` item arrays, and content-file key order. Nothing enforces that they agree except developer discipline.

## 2. Main Flow

| Step | Actor | Action | System Response |
|------|------|------|------------|
| 1 | `admin` | Opens **Navigation** | Sections listed, each with its pages in current order |
| 2 | `admin` | Drags a page to a new position | New order previewed (**FR-NAV-001**) |
| 3 | `admin` | Edits a navigation label | Label changes; the page **title is unaffected** (**FR-NAV-002**) |
| 4 | `admin` | Saves | One explicit order value written per page (**FR-NAV-004**); P95 < 2s |
| 5 | System | — | Reader navigation renders from the database (**FR-NAV-005**) |

## 3. Alternative Flow

### 3.1 A-1: Move a page between sections (**FR-NAV-003**)
- Action: drag a page into a different section
- Outcome: the page URL changes, so a permanent redirect is created from the old path (**FR-READ-003**)

### 3.2 A-2: Add a badge (**FR-NAV-006**)
- Action: mark a page "New"
- Outcome: badge appears in reader navigation, matching today's `flow` page behaviour (`Sidebar.tsx:497`)

## 4. Exception Flow

### 4.1 E-1: Concurrent reordering
- Two admins reorder the same section at once
- Action: the second save is rejected with a refresh prompt (same optimistic-locking rule as FR-CONT-013)
- Outcome: no interleaved, nonsensical ordering

### 4.2 E-2: Empty label
- Action: rejected — a label is required for the page to be reachable in navigation

### 4.3 E-3: Section emptied by a move
- Action: allowed but flagged; an empty section renders no navigation entries

## 5. Non-Functional Requirements Mapping

| NFR-ID | Application |
|--------|------|
| NFR-USE-02 | Drag and drop; no arrays, no code, no deploy |
| NFR-PERF-02 | Step 4 save completes P95 < 2s |
